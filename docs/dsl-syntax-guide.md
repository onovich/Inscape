# Inscape 语法说明

状态：当前作者指南

本文面向脚本作者，解释 Inscape 当前“已经能写、已经能用”的语法。它不替代 [DSL 语言设计草案](dsl-language.md)；如果你关心候选语法、长期边界和未定项，再回去看设计文档。

## 一眼看懂

Inscape 当前可以先理解成五类东西：

1. `# 标题`
   - 定义一个可跳转的剧情块；旧项目里的 `:: node.name` 仍兼容。
2. `角色：对白` / `旁白文本`
   - 写剧情正文。
3. `? 提示` + `- 选项 -> target`
   - 写选择与分支。
4. `-> target`
   - 显式跳到别的节点。
5. `@...` 与 `[...]`
   - `@` 写事件、动作、时机和状态变化；`[]` 在正文里查询/读取当前值。

## 最小例子

```inscape
# 法庭开场

@entry
@scene courtroom
@timeline.talking.exit court_intro

旁白：法庭里很安静。
成步堂：[player.name]，先从证言开始吧。

? 你要做什么
- 询问证言 -> 询问证人
- 查看证物 -> 查看证物

# 询问证人

证人：我什么都不知道。
-> 法庭开场
```

## 1. 节点：`# 标题`

节点是 Inscape 的基本叙事块。

```inscape
# 法庭开场
```

规则：

- 标题是作者可见的剧情块名称。
- 项目内标题必须全局唯一。
- `# 标题` 本身结束上一个节点并开始新节点。
- 标题前建议留一个空行；漏空行只会产生 style hint，不会阻止编译。
- 旧 `:: node.name` 仍兼容，用于旧项目和迁移期。

你可以把标题理解成“这个剧情页给人看的名字”。长期机器身份由 stable node id 维护，详见 [Stable Node ID Contract](stable-node-id-contract.md)。

## 2. 正文：对白与旁白

### 对白

```inscape
成步堂：异议！
Witness: I know nothing.
```

当前写法是“说话人 + 冒号 + 文本”。

- 支持全角 `：` 和半角 `:`。
- 冒号前面会被识别为 speaker。
- 冒号后面的部分是正文文本。

### 旁白

```inscape
法庭里一片安静。
```

没有 speaker 的普通文本会被当作旁白/叙述行。

## 3. 选择：`?` 与 `-`

### 选择提示

```inscape
? 你要做什么
```

`?` 行是这一组选项的提示语。

### 选择项

```inscape
- 询问证言 -> court.questioning
- 查看证物 -> court.evidence
```

含义是：

- `-` 后面是玩家看到的选项文本。
- `->` 后面是选中后跳转的目标节点。

如果只有选项，没有单独的 `?` 提示，也可以直接写 `-` 行。

## 4. 跳转：`-> target`

```inscape
-> court.opening
```

这是显式跳转。

- 它不会显示给玩家。
- 它只是告诉叙事流程“下一步去哪个节点”。
- 在 VSCode 里可 Ctrl+Click 跳到目标节点。

## 5. `@...` 是什么

> 2026-05-16 语义收敛提示：后续推荐把 `@` 理解为事件、动作、时机和状态变化，把 `[]` 理解为查询、读取和文本插值。历史 `[timeline: ...]` / `[kind: alias]` 写法仍是兼容事实，但不再是新设计的推荐心智模型。详见 [Authoring Marker Contract](authoring-marker-contract.md)。

`@` 行是 **事件、动作、时机或元信息标记**。

它的核心意思是：

- 这不是给玩家看的正文。
- 它优先表达入口、事件、动作、时机、状态变化或宿主可读意图。
- 它是给编译器、预览、宿主桥接层、编辑器提示的轻量结构标记。

### 常见例子

#### `@entry`

```inscape
@entry
```

表示“这个节点是项目入口”。

- 预览默认从这里开始。
- 项目编译默认把它当入口节点。
- 它不显示给玩家。

#### `@scene courtroom`

```inscape
@scene courtroom
```

表示“这个节点带有一个 scene 语义标签”。

- 当前更偏作者意图/宿主提示。
- 它本身不改变正文流程。
- 后续宿主层可以用它做分组、资源准备、逻辑标注。

#### `@timeline court_intro`

```inscape
@timeline court_intro
@timeline.talking.exit court_outro
@timeline.node.enter camera_push
```

表示“这里在指定时机触发一个宿主侧演出事件”。

当前要点：

- 它不是 DSL 内建的时间轴脚本语言。
- 它只表达宿主演出事件的可读 ID 和触发时机。
- 这些 ID 最终应通过 Host Bridge / legacy binding map 映射到项目内部资源或事件处理器。

## 6. `[...]` 是什么

> 2026-05-16 语义收敛提示：`[]` 的长期主线是读取当前上下文并拼进玩家可见文本，例如 `[player.name]`、`[itemName]`、`[player.gold]`。普通静态人名、物品名和地点名不要强行包成结构化标签；会触发宿主行为的内容优先使用 `@`。

`[]` 是 **文本内查询 / 插值标记**。

它属于玩家可见文本的一部分，用来从当前上下文读取值并拼进文本。

### 基本写法

```inscape
旁白：[player.name]推开了门。
系统：获得了[itemName]。
老板娘：还剩[player.gold]枚金币。
```

可以把它理解成：

- `player.name`：读取玩家显示名。
- `itemName`：读取刚刚获得物品的显示名。
- `player.gold`：读取当前数值。

当前语义：

- `[]` 主要是查询 / 读取 / 文本插值。
- 它不负责触发事件、修改状态或调度宿主资源。
- 静态人名、物品名、地点名不需要强行包成 `[]`。

### 兼容旧写法

历史原型中存在这类 inline host binding 写法：

```inscape
[bg: courtroom]
[timeline: court_intro]
[timeline.node.exit: court_outro]
```

这些写法当前仍可能被 VSCode 或 UnitySample 兼容识别，但不再作为新设计的推荐模型。新写法中，事件和时机优先用 `@...`，玩家可见文本里的动态值才用 `[]`。

## 7. `@` 和 `[]` 的区别

> 2026-05-16 当前推荐一句话：`@` 负责改变世界，`[]` 负责读取当前上下文并拼进文本。下面保留的宿主绑定说明描述的是历史原型能力和兼容行为，不应继续扩大为新写法。

可以先这样记：

- `@...`
  - 更像“节点级/语义级元信息”。
  - 例如入口、场景、Timeline hook。
- `[...]`
  - 更像“文本内查询 / 插值”。
  - 例如玩家名、刚获得物品名、当前金币数。

更直白一点：

- `@` 偏“这里要发生什么、何时发生、改变什么”。
- `[]` 偏“这里要读取什么值并显示出来”。

旧的 `[kind: alias]` 写法仍属于兼容提示层，不是新推荐的事件模型。

### 一句判断题

如果你写这一行时，脑子里的问题是：

- “这个 block / 这个位置会触发、授予、设置、播放或声明什么时机？”
   - 更偏用 `@`
- “这段玩家可见文本里要读取哪个当前值？”
   - 更偏用 `[]`

### 再直白一点

- `@` 回答的是“这里发生什么”
- `[]` 回答的是“这里显示什么值”

### 目前真正比较‘有硬作用’的情况

#### `@` 里当前最有明确作用的

- `@entry`
   - 真正影响编译器/预览入口。
- `@timeline... alias`
   - 真正表达“在这个节点/这句对白的某个 phase 上挂一个 hook”。

#### `@` 里当前更像标签的

- `@scene xxx`
   - 目前主要是语义标签。
   - 它现在还没有像 `@entry` 那样的强约束效果。

所以你觉得“`@` 好像没啥用”并不是错觉：

- 在当前阶段，`@entry` 很有用。
- `@timeline...` 也有明确用途。
- 但像 `@scene` 这样的项，确实还更偏作者标签，而不是强执行语义。

#### `[]` 当前最适合的

- `[player.name]`
   - 读取玩家显示名。
- `[itemName]`
   - 读取刚刚产生的显示值。
- `[player.gold]`
   - 读取当前上下文数值。

所以 `[]` 的主战场不是静态资源别名，而是玩家可见文本里的动态值。

### 不要把它们理解成这两句话

- “`[]` 就是资源别名”
- “`@` 就只是标记当前 block”

这两句都只说对了一部分。

更准确地说：

- `[]` 主要是查询 / 插值，不负责触发事件。
- `@` 主要表达事件 / 动作 / 时机 / 状态变化，不只标记 block。

### 当前推荐用法

- 入口声明：用 `@entry`
- block 的语义标签：用 `@scene xxx`、其他 `@metadata`
- 需要表达 hook 时机：优先用 `@timeline.<phase> alias`
- 需要表达动态文本值：用 `[player.name]`、`[itemName]`、`[player.gold]` 这类查询 / 插值
- 旧项目里的 `[kind: alias]` 作为 legacy inline host binding 保留兼容，不作为新推荐写法

## 8. 注释

当前原型使用：

```inscape
// 这是一行注释
```

注释不会进入剧情正文。

## 9. 一个稍完整的例子

```inscape
:: court.opening

@entry
@scene courtroom
@timeline court_intro

旁白：法庭里很安静。
成步堂：[player.name]，先从证言开始吧。

? 你要做什么
- 询问证言 -> court.questioning
- 查看证物 -> court.evidence

:: court.questioning

证人：我什么都不知道。
成步堂：那就从头再问一遍。
-> court.opening

:: court.evidence

旁白：证物袋里只有一枚旧怀表。
```

## 10. 当前不要误会的边界

这些东西现在 **还不是** 第一版 DSL 的既定能力：

- 变量系统
- 条件分支表达式
- 自定义指令系统
- 直接控制 Unity / Bird API
- 在 DSL 里描述完整 Timeline 内部轨道

第一版更像：

- 图叙事结构
- 正文与选项
- 轻量元信息
- 宿主事件 / 查询插值提示
- 预览与工具链验证

## 11. VSCode 里你会看到什么

当前扩展里：

- `@...` 和 `[...]` 都有高亮与 Hover。
- `@timeline ...` 可 Ctrl+Click 到绑定来源；legacy `[kind: alias]` 仍保留兼容导航。
- `@entry`、`@scene` 会显示“这是 metadata”的解释。
- 正文文本 Ctrl+Click 可以打开或刷新预览，并定位到对应节点页面。
- 预览里的 `源码` 按钮会尽量复用已经打开的源码编辑器。
